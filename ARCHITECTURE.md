# Architecture

## 1. What lives where

Each feature owns a folder with its pure logic and its canvas painting together; a component or hook that needs React lives in the same folder. Tests sit next to the code they test (`labels/paintLabels.test.ts`), never in a separate tree.

| Folder / file | Holds |
|---|---|
| `viewport/` | `viewport.ts` (the `Viewport` transform: `toScreen`, `toWorld`, `panBy`, `zoomAt`, `zoomTo`, `clampScale`, `recenterOnBoxChange`: the showcase's keep-the-view-on-resize transform), `fit.ts` (`worldBounds`, `sceneBounds`, `ringBounds`, `fitSpec`, `fitBounds`, `fitClamped`: the padded fit-to-extent computation, factored so the minimap and the legend's territory zoom can share it), `fitScene.ts` (`fitScene`: the first view, fitted to territory shapes and to the names drawn at that scale, refined over `LABEL_FIT_PASSES`), `wheel.ts` (`wheelZoomFactor`: a pure, `deltaMode`-normalised, `Tuning`-driven zoom factor per wheel event), `publicViewport.ts` (`MapViewport`, the box-independent public view: `toPublic`, `fromPublic`, `sanitise` to the wheel band, `sameView` within a relative 1e-9) and `useElementSize.ts` (the hook: a `ResizeObserver` on a ref, `null` until the first measurement, used by `CorpusMap` when `width`/`height` are not given) |
| `lod/` | `lod.ts` (`Regime`, `LodThresholds`, `DEFAULT_THRESHOLDS`) and `regime.ts` (`regimeAt`, the hysteresis regime transition, and `fade`, the zoom-driven cross-fade) plus `visible.ts` (`visibleNodes`: on-screen filter plus the hard render cap) |

| `shared/` | `spec.ts` (`MapNode`, `MapSpec`, `Territory`, `validateSpec`), `surface.ts` (`Surface` interface, `RecordingSurface` for tests, `canvasSurface` for the browser), `theme.ts` (`Theme`, `DEFAULT_THEME`, `DARK_THEME`), `presentation.ts` (`Presentation`, `resolvePresentation`: guided at the far regime and dense at mid and near unless the `presentation` prop locks one), `corner.ts` (`Corner` and its offsets, shared by the minimap and the legend), `dimmed.ts` (`DIMMED_ALPHA`, `NO_DIMMED`), `insets.ts` (`Insets`, `normaliseInsets`, `usableArea`: the part of the box a consumer overlay covers, honoured by edge markers and `reveal` but never by the fit, so the zoom ratio does not move when an overlay opens), `tuning.ts` (`Tuning`, `DEFAULT_TUNING`, `resolveTuning`: every number the literature does not settle, validated and defaulted in one place), `scene.ts` (`Scene`, `buildScene`: see section 3) and `paint.ts` (the compositor, see section 3) |
| `CorpusMap.tsx` | The component: the box (explicit `width`/`height`, or the parent measured through `viewport/useElementSize.ts`, with a keep-view resize), pointer and wheel handling, viewport and regime state (controlled or not, through the one `requestViewport` gate), the selection and the open territory, the imperative handle (`CorpusMapHandle`: `zoomIn`/`zoomOut`/`fit`/`reveal`) and `onViewChange`; drives the canvas ref through `paint()` and renders `CardOverlay`, `AccessibleTree`, the optional `Minimap` and the optional `Legend` alongside it |
| `index.ts` | The public door, see section 4 |

Outside `src/`: `fixtures/synthetic/generate.ts` is a seeded generator (`generateCorpus`) used by tests and the benchmark, never shipped; `scripts/` holds `api-guard.mjs` and `size.mjs`, the two gates described in sections 4 and 7.

## 2. The one rule: decisions are pure

A `.ts` file in `src/` that is not a hook (a file named `use*.ts`) may not import `react` or `react-dom`, and may not read `window` or `document` — it decides, it does not act. Components (`.tsx`) and hooks are the only places that touch React or the DOM, and they apply what the pure code already decided. The rule is enforced by ESLint's `no-restricted-imports` and `no-restricted-globals` in `eslint.config.js`, scoped to `src/**/*.ts` and excluding `use*.ts` and test files, and is proven by a canary: a plain pure file with `import React` or a bare `document` reference fails lint.

## 3. Scene and paint order

`shared/scene.ts`'s `buildScene` computes everything about a corpus that does not change with the viewport — territory boundary shapes (`territories/shape.ts`) and placed territory names (`labels/placement.ts`, anchored by `labels/pole.ts`), the families' regions and colours (`groupShapes`, `groupBounds`, `groupColours`, empty without groups) and each item's related items (`related`, `maximumEdgeWeight`, empty without edges) — once per spec, not once per frame. `CorpusMap` memoizes the resulting `Scene` on the primitive `tuning`/`theme` fields `buildScene` actually reads, not on the `tuning`/`theme` objects themselves (both are minted fresh on every render for an inline literal prop), so a scene rebuild — measured at 70-135ms on 10,000 items — only happens when a value it depends on actually changes; a box resize alone is not one of those values (see below). Per-frame values that a precomputed `Scene` cannot carry (the current regime, the point layer's fade, the canvas's CSS size) travel separately as a small `Frame` object; `paintLabels` uses the size to skip a name wider or taller than the canvas, which could never be read whole there. The decision never depends on where a name sits: a name that fits slides off the edge clipped by the canvas, because a position-dependent skip makes names pop out on pan and zoom (map-feel metric 7, measured on the real canvas, and the painted pop sweep in `demo/corpora/arxiv.test.ts`).

Each `PlacedLabel` carries its own `activeFromScale` — the absolute viewport scale (`Viewport.scale`'s own units) at which the label starts drawing, not a ratio of the fitted scale — so `paintLabels` compares it straight against `vp.scale` with no `fitScale` in the call at all. This is what lets a box resize skip a scene rebuild: resizing only ever changes `fitScale`, and once the active range is stored in absolute units a resize has nothing left in the scene to invalidate (closed the residual noted in `BACKLOG.md` from the map-feel review). `buildScene` itself no longer takes a `fitScale` argument.

`shared/paint.ts` is the only place that orders drawing: clear, then the territory fill layer (largest territory first, one composite at the fill alpha, halved in dense), then territory outlines, then the families' outlines when there are groups (the leaves' fill layer and the families' fill layer cross-fade by `Frame.groupAlpha`, so far views read as families and near views as leaves; a spec without groups paints exactly as before), then points (disc or ring), then the item labels at near (`labels/paintItemLabels.ts`: each drawn plate an open tooltip, at `Frame.itemLabelAlpha`, inside the point layer so a name still paints over it), then the hovered item's edges at half the point alpha and the selected item's edges (`edges/paintEdges.ts`), then the selection ring, then the keyboard-focus outline (`a11y/paintFocus.ts`: the focused territory's rings, or a ring around the focused item's point, in `theme.focusOutline`/`focusOutlineWidth`), then names (dense presentation keeps large names at full emphasis and mutes medium and small ones; with groups, group names are drawn at `Frame.groupAlpha` and territory names at the rest, so the two levels cross-fade around `tuning.groupNamesUntil`; a dimmed territory's fill, points and name are drawn at `DIMMED_ALPHA` of their alpha), so a name is never covered by a mark, by a later territory's fill or by the focus outline. The focused ids reach it through `Frame` as primitives (`focusedTerritory`, `focusedNode`), each painted only in the regime where its button is listed. A feature that wants to draw something adds its `paint*` function in its own folder and one call to it, in the right position, in the compositor — nothing else decides paint order, and nothing paints outside this function.

## 4. The public door

Only `src/index.ts` is the library's API; anything not re-exported from it, however public the file looks, is internal and may change without notice. `api/corpus-map.api.d.ts` is a committed snapshot of every `.d.ts` file `npm run build` produces, concatenated in sorted path order, and `npm run api:check` (run in CI) rebuilds and diffs against it — any difference, including one buried in a feature file `index.ts` only re-exports, fails the build. `npm run api:update` rebuilds and rewrites the snapshot, which then shows the change in the commit diff for review.

## 5. Testing each layer

Pure functions get plain unit tests, colocated with the function. Drawing functions are tested against `RecordingSurface`, which records every call into typed arrays (`polygons`, `circles`, `texts`) and an ordered `calls` log, so a test can assert both content and sequence. Components are tested with Testing Library in jsdom; jsdom has no canvas, so `test/setup.ts` stubs `HTMLCanvasElement.prototype.getContext` to return `null` (which `CorpusMap` already handles), and a test that needs to see what was drawn installs a fake 2D canvas context (`recordingContext` in `src/CorpusMap.test.tsx`) that records `fillText` calls in `HTMLCanvasElement.prototype.getContext`'s place. Performance is `npm run bench`, which runs the compositor against 10,000 items from the synthetic generator under its own Vitest config (`vitest.bench.config.ts`), outside the coverage-gated suite.

## 6. Adding a feature

1. Give it a folder under `src/`, named for the feature, not the file type.
2. Write the pure logic and its test first; keep it free of React and the DOM per section 2.
3. Add a `paint*` function and its line in `shared/paint.ts`, or a component that consumes the pure logic.
4. Export from `index.ts` only if it is meant to be public, then run `npm run api:update` and review the diff.
5. Add a changeset (`npx changeset`) describing the change for consumers.
6. Run the full gate locally before committing: `npm test`, `npm run lint`, `npx tsc --noEmit`, `npm run build`, `npm run api:check`, `npm run size`.

## 7. Why these tools

Biome formats everything and owns almost every lint rule, including its React/JSX ones (`useJsxKeyInIterable`, `noArrayIndexKey`, and the rest of its `react` domain); the only two Biome turns off are `correctness.useExhaustiveDependencies` and `correctness.useHookAtTopLevel`, in `biome.json`, because ESLint owns hooks. ESLint carries only `eslint-plugin-react-hooks` (rules of hooks, exhaustive deps, the render-purity rules) plus the pure/React boundary rule from section 2, nothing stylistic. ESLint parses TypeScript through Babel (`@babel/eslint-parser`, `@babel/preset-typescript`) rather than `typescript-eslint`, because TypeScript 7 no longer exposes a JavaScript compiler API and `typescript-eslint` cannot parse without one; the Babel parser's own ceiling is ESLint 9, which is why ESLint is pinned there.

## 8. The arXiv corpus pipeline

`pipeline/arxiv/` is a separate, uv-managed Python package that builds the real-world corpus the demo ships: `demo/corpora/arxiv.json` (a `MapSpec`, checked by `export.py` and again by `demo/corpora/arxiv.test.ts`'s `validateSpec`) and `demo/corpora/arxiv.meta.json` (how and when it was produced). It fetches `cs.*` papers from the live arXiv API through a `fetch → embed → project → export` pipeline, cached stage-by-stage so a failed run re-runs just the failed stage. It has its own gates, run from `pipeline/arxiv/`: `uv run pytest` (100% coverage gate), `uv run ruff format --check .`, `uv run ruff check .`, `uv run mypy src tests` — none of this runs in this repository's `npm test`/`npm run lint`, and it is not part of the library `corpus-map` ships. The pipeline runs once locally against the live API; its output is committed like any other fixture, not regenerated in CI. See `pipeline/arxiv/README.md` for how to re-run it.

## 9. The demo

`demo/` is a Vite app outside `src/`, consuming the library through a Vite alias (`corpus-map` → `src/index.ts`), never through the built package. `App.tsx` owns the top-level state (the active corpus, the async load result for arXiv, the view reported by `onViewChange`, the tuning-panel values, kept per corpus in `edits` and resolved from each gallery entry's `display` over the library defaults by `demo/corpora/display.ts`) and lays out `demo/components/`: `TopBar` (corpus picker plus the tuning-panel gear button), `ZoomControls` (drives the library's own `CorpusMapHandle`), `Indicator` (renders `onViewChange`'s payload, nothing computed), `Footer` (the arXiv/synthetic disclosure), `Drawer` (the selected-item panel, with an arXiv-specific layout guarded to only ever link an `https://arxiv.org/abs/` URL), and `TuningPanel` (every `Tuning`/`LodThresholds`/`cardSize` control, validated through the library's own exported `resolveTuning`/`resolveThresholds`, plus `WheelCapture`, a passive listener recording the last 50 wheel events for reading what a real trackpad or mouse sends). `demo/corpora/index.ts`'s `gallery` is the one list both the picker and `demo/corpora.test.ts` read; arXiv is the only entry that loads lazily (a `fetch` of `arxiv.json`, emitted as its own asset and kept out of the main bundle; `fetch` rather than `import()`, because a browser caches a failed dynamic import and a retry could never succeed) and the default (first) entry. Each entry may carry `display` (`tuning`, `thresholds`, `cardSize`); its `nearAt` is the value metric 18 (`demo/corpora/nearAt.test.ts`, measured by `demo/corpora/labelledShare.ts`) picks for that corpus, and the card size defaults to `demo/cards.tsx`'s `cardSizeOf`, the library's `cardSizeFor` over the titles that corpus's renderer shows (also in `demo/cards.tsx`). The tuning panel's Copy settings copies the current values in that `display` shape: only the tuning and thresholds that differ from the library defaults, and the card size only when it differs from the computed one. Its body goes through `arxivSpec`: `withExpandedArxiv` (the compact edges, territory members and node `meta`: year, abstract url and the arXiv category from the body's `categories` table, which the arXiv card and drawer show), then `validateSpec`; its territories are the pipeline's clusters, leaves under declared families, so no group names are applied at load; the arXiv and colouring tests build their spec through the same function, so they test what the demo loads.

Every one of those components that floats over the map (`data-floating-control` in `App.tsx`'s render) is required, by `demo/App.test.tsx`, to declare its own box in real CSS (`position: fixed`/`absolute` plus a `width`/`maxWidth` and a `left`/`right`) rather than relying on a container to imply one — `demo/components/floatingLayout.ts` centralises the shared geometry (minimap size and margin, the indicator's estimated content width, the gutter) that `Indicator`'s own position, `ZoomControls`' shift-left-of-the-drawer decision and the test's pairwise collision sweep all read, so they can never drift into two hand-kept copies of the same numbers. jsdom has no layout engine, so this is a check on declared geometry, not rendered geometry; a real-browser layout assertion is a `BACKLOG.md` item.

## 10. The group-names tool

`tools/group-names/` is a maintainer tool outside `src/` (like `fixtures/`), so nothing in it ships; it names a corpus's derived groups with Claude, offline and once, and its output is committed. Pure modules, each tested: `prompt.ts` (`buildGroupNamesPrompt`: per group, its id, its members with their item counts and up to eight sample labels taken round-robin, under `GROUP_NAMES_PROMPT_VERSION`), `names.ts` (`parseGroupNames`: every naming rule, at most 24 characters, distinct, never "Other"), `groupNamesFile.ts` (the `GroupNamesFile` shape, `toGroupNamesFile`, and `withGroupNames`, the load transform, which leaves the body untouched unless it is a valid spec declaring no `group` or `parent` and `staleGroups` finds nothing) and `stale.ts` (`staleGroups`: what changed between the file and what the corpus derives today, matched one named group per derived group, plus any name the rules refuse, through the parser's own `groupNameProblem`). Then one thin network call, `claude.ts` (`requestGroupNames`, through `@anthropic-ai/sdk`, a devDependency, with a JSON-schema output, `effort: "high"` and `fallbacks: "default"`; the client is injected, so tests run a real client over a fake `fetch`), and one thin CLI, `cli.ts` (`runGroupNames`, every file, environment and client access injected through `GroupNamesIo`), behind `main.ts`, the only file that touches the runtime. The package has no `@types/node` on purpose (a browser library: node types would leak into `src/`), so `main.ts` declares `process` itself and loads `node:fs/promises` through a variable specifier the type checker does not resolve. The SDK refuses a browser-like environment, so `claude.test.ts` and `cli.test.ts` run under `// @vitest-environment node`.
